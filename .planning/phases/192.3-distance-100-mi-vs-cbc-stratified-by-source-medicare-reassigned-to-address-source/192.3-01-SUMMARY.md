## Key Structural Finding: Phase Goal Reframing

The original phase title refers to "Medicare reassigned to address source." The step-0 probe establishes that **this framing does not apply to this extract** — there are no Medicare or payer-type SOURCE codes.

The analytic question is reframed as: **stratify the distance >100 mi vs CBC association by data partner SOURCE**, using the in-effect address SOURCE as the analytic SOURCE where an address record exists, and the encounter's own SOURCE as the fallback for unmatched encounters.

The `assign_analytic_source()` function in Plan 02 will implement:

1. `interval_match` encounters: use `addr_source_effective` (in-effect address SOURCE at ADMIT_DATE).
2. `recency_fallback` encounters: use `addr_source_effective` (most-recent-before address SOURCE).
3. `no_match` encounters: use the encounter's own SOURCE (no address record available; UCI encounters remain UCI).

No Medicare-to-address-SOURCE reassignment branch is needed. The CONFIG key is set to `character(0)` as a documented no-op.

- **Found during:** Task 1
- **Issue:** Plan specified R192_CBC_EVENTS_RDS and R192_ANCHORS_RDS as mandatory env-var pins with `stop()` guards, but these RDS files are never written by R/165 or any upstream script. R192_CBC_EVENTS_RDS and R192_ANCHORS_RDS env-vars are supported as optional RDS overrides (loaded if set and file exists), consistent with the plan's intent while not blocking the first run.
- **Files modified:** R/192_source_step0_probe.R

## D-192.3-05: Medicare/Claims Trigger Mechanism — RESOLVED

**Status: RESOLVED — Option A selected**

**Decision:** Use `CONFIG$claims_source_codes = c("FLM")` as the reassignment trigger.
- FLM = Florida Medicaid administrative claims feed — the only claims/payer-based data partner in this extract.
- `CONFIG$medicare_source_codes = character(0)` retained as a documented no-op (lookup was performed; no Medicare-specific SOURCE code exists).
- Reassignment chain in `assign_analytic_source()`: address SOURCE → modal SOURCE from **non-claims** encounters only → `"Claims_unresolved"` (renamed from the earlier "Medicare_unresolved" draft).
- Sensitivity: add sheet pair `BY_SOURCE_pat_flm` / `BY_SOURCE_enc_flm` where FLM encounters are kept as their own stratum without reassignment — directly tests the "CBC captured outside our system" hypothesis.

**Rationale:** Option A is the most targeted — it identifies the actual structural reason FLM encounters may have a different address SOURCE (claims data lacks encounter-level geography; the patient's residence record is the better locator). Option B (payer type) would require an additional DuckDB column and conflates insurance type with data feed type. Option C changes the estimand.

**Payer-type probe (`R/192b_payer_type_probe.R`) — QC context only**

The probe was written and committed but its results were not decision-driving for this choice. It remains available as a QC tool to verify that FLM encounters are predominantly Medicaid-payer-typed (expected) and to flag any non-FLM encounters with Medicare payer type that may warrant future follow-up. Run it after Plans 02–03 complete if payer-type stratification is of interest.
