  <context>
    CONTEXT.md §3b and RESEARCH confirm SVI must be DERIVED. The recommended path (D-02a) needs a build
    script, a per-ZCTA `svi_areal_coverage` column, and an NA floor (0.80 suggested). findSVI (CRAN) computes
    ZCTA SVI directly from ACS but requires a Census API key — 146-DISCOVERY.md records whether one is available.
    County-level (D-02b) is much coarser and must NOT be silently placed in the same column as tract-derived
    values. Dropping (D-02c) is honest but loses a column.
  </context>
  <options>
    <option id="D-02a">
      <name>Derive by population-weighted areal mean (findSVI if API key available, else HUD USPS crosswalk)</name>
      <pros>Correct ZCTA-level measurement; keeps SVI in the deliverable; carries a coverage share</pros>
      <cons>Real work: build script + derived file + coverage floor; needs Census API key or HUD crosswalk</cons>
    </option>
    <option id="D-02b">
      <name>Use county-level SVI joined via ZIP5 -> county</name>
      <pros>Cheap, no derivation</pros>
      <cons>Much coarser; a county spans different neighbourhoods; arguably too coarse to report</cons>
    </option>
    <option id="D-02c">
      <name>Drop SVI from the deliverable</name>
      <pros>Honest; removes a column nobody can populate correctly right now</pros>
      <cons>Three indices become two</cons>
    </option>
  </options>
