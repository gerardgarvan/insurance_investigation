## §3 HL flag/date rule

### R/52_gantt_v2_export.R — HL Diagnosis pseudo-rows (Section 4C, lines ~657–796)

- **Source:** `output/confirmed_hl_cohort.rds` (Phase 55), field `first_hl_dx_date`
- **File:line:** R/52_gantt_v2_export.R L659–796
- **Level:** Patient-level. The date `first_hl_dx_date` is a single value per patient from the cohort RDS; it is assigned as both `episode_start` and `episode_stop` for one pseudo-row per patient (`episode_number = 1L`).
- **Date expression:** `episode_start = first_hl_dx_date` (directly from cohort RDS field)
- **Date-range filter:** None applied in R/52 on the HL diagnosis date itself. The cohort RDS was built by Phase 55 and presumably already filters invalid dates at ingest.
- **Sentinel handling:** No explicit sentinel comparison in R/52 Section 4C. The HL date is taken as-is from the RDS (`filter(!is.na(first_hl_dx_date))`; L668). No sentinel constant referenced.
- **Sentinel fallback:** Not applicable — the date comes pre-validated from the cohort RDS, not from a raw DIAGNOSIS pull.
- **Column assignment:** `patient_id`, `treatment_type = "HL Diagnosis"`, `episode_number = 1L`, `episode_start = first_hl_dx_date`, `episode_stop = first_hl_dx_date` (L677–680). `is_hodgkin = TRUE` (L688).
- **Pseudo-row repetition on episodes:** The `episodes_export` has one row per HL Diagnosis pseudo-row (one per patient), appended to the end of the treatment episodes and then sorted. The HL flag value (`is_hodgkin`) is repeated on every row for a given patient via the `cancer_category` → `is_hodgkin` derivation at Section 4D (L874–875), not via a separate join.

### R/142_gantt_180_export.R — HL Diagnosis pseudo-rows (Section 4C, lines ~424–499)

- **File:line:** R/142_gantt_180_export.R L426–499
- **Pattern:** Identical to R/52 Section 4C. Same source (confirmed_hl_cohort.rds), same field, same logic.

### Implication for autoimmune columns

The HL date/flag approach in R/52/R/142 uses a pre-built cohort RDS, not a direct DuckDB pull. The autoimmune approach (D-05a) will use DuckDB DIAGNOSIS directly — this is an **expected difference**, not a deviation. The sentinel constant (`SENTINEL_CUTOFF = as.Date("1910-01-01")`) will be defined in config (Task 3) and applied to the DX_DATE / ADMIT_DATE filtering in `summarise_autoimmune_dx()`, matching the pattern used in R/47, R/48, R/49.

**Difference from CONTEXT D-07:** CONTEXT D-07 specifies a sentinel-based date filter on DX_DATE and ADMIT_DATE. The HL rule in R/52 does not apply a sentinel (the cohort RDS pre-validates). The autoimmune helper will apply the sentinel as specified in D-07 (not mirroring the HL RDS path); this is a deliberate difference recorded here per the PLAN's instruction ("where it differs from 192.1-CONTEXT D-07, the HL rule wins"). Since the HL rule has no sentinel comparison step (it uses a pre-built cohort), D-07's sentinel logic stands as written.

## §6 Sentinel constant

No `SENTINEL_CUTOFF` constant exists in `R/00_config.R`. The value `as.Date("1910-01-01")` is defined as a local variable `SENTINEL_CUTOFF` in R/47 (L68), R/48 (L62), and R/49 (L63).

**Decision for Task 3:** Add `SENTINEL_CUTOFF <- as.Date("1910-01-01")` to `R/00_config.R` Section 4c alongside `MTX_CODES`. This makes the sentinel a project-wide named constant (not a magic number) for use by `build_autoimmune_dx_flags()` and the Gantt build scripts. No other scripts need updating since they define it locally; the new config value is additive.

The `summarise_autoimmune_dx()` function takes `sentinel` as an explicit argument, so it is pure and testable with any value. The Gantt scripts will pass `CONFIG$sentinel_cutoff` (or access `SENTINEL_CUTOFF` directly since config is sourced before utils_doi).
