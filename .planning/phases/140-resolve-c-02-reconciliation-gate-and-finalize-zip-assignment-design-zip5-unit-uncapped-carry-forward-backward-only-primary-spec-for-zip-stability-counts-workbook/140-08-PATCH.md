## FIX-01 [M] — `gap_days_at_assignment` is NA for 92% of S2 encounters

**Target:** 140-05 Task 1.

**Defect.** The planned `case_when` sources S2's gap from `s2_nearest_backward`, which by
construction covers only encounters with a **backward** `zip5_seq` spell. 201,118 of
217,570 S2 encounters (92%) are forward-only. For those, `gap_days_s2` is NA; they are not
`has_direct_zip5_only`, so `gap_days_s3` is also NA; the branch falls through to
`NA_real_`.

The largest resolved bucket under the forward-inclusive specification therefore receives no
covariate value, failing P-04a's acceptance wording ("Variable present, one value per
assigned encounter").

Compounding it: the plan's `<interfaces>` sign convention promises negative values signal
forward inference, but nothing in the S2 path can produce a negative — `s2_nearest_backward`
is backward-only. Only the S3 path could ever go negative, so the documented convention is
unreachable for the majority of encounters it describes.

**Change.** `s2_matches` (SECTION 11, ~line 887-894) already carries a `direction` column
covering both sides. Reduce it to a nearest-either-direction companion alongside the
existing backward-only reduction. Add after `s2_nearest_backward`:

```r
# 140-08-PATCH FIX-01: nearest zip5_seq spell in EITHER direction, for the
# forward-inclusive gap covariate. s2_nearest_backward (above) stays as-is and feeds
# the backward-only covariate -- two reductions, not one reused for both.
s2_nearest_any <- s2_matches %>%
  mutate(
    gap_signed = as.numeric(ADMIT_DATE - period_start_dt),
    .tie_rank  = if_else(gap_signed >= 0, 0L, 1L)   # FIX-08: backward wins exact ties
  ) %>%
  group_by(ID, ENCOUNTERID, ADMIT_DATE) %>%
  arrange(abs(gap_signed), .tie_rank, .by_group = TRUE) %>%
  slice_head(n = 1) %>%
  ungroup() %>%
  select(ID, ENCOUNTERID, ADMIT_DATE, gap_days_s2_any = gap_signed)
```

Apply the identical pattern to `s1_matches`, producing both `s1_nearest_any` (as planned,
but with the FIX-08 tiebreak) and a new `s1_nearest_backward` (`filter(direction ==
"backward")` before the reduction).

## FIX-02 [M] — one gap column, two scenario assignments

**Target:** 140-05 Task 1; frontmatter `must_haves.truths` and `artifacts`.

**Defect.** 140-04 produces `scenario_assigned` and `scenario_assigned_backward_only`.
140-05 produces a single `gap_days_at_assignment`. Which record resolved an encounter
differs between the two specifications — a forward-only S2 encounter is resolved under
forward-inclusive and unresolvable under backward-only, so its gap must be a value in one
and NA in the other. A single column cannot represent both.

**Change.** Compute two columns, each independently, mirroring 140-04's treatment of the
two waterfalls:

```r
encounter_zip <- encounter_zip %>%
  left_join(s2_nearest_backward %>%
              transmute(ID, ENCOUNTERID, ADMIT_DATE,
                        gap_days_s2_bwd = as.numeric(ADMIT_DATE - period_start_dt)),
            by = c("ID", "ENCOUNTERID", "ADMIT_DATE")) %>%
  left_join(s2_nearest_any,      by = c("ID", "ENCOUNTERID", "ADMIT_DATE")) %>%
  left_join(s1_nearest_backward, by = c("ID", "ENCOUNTERID", "ADMIT_DATE")) %>%
  left_join(s1_nearest_any,      by = c("ID", "ENCOUNTERID", "ADMIT_DATE")) %>%
  mutate(
    # Forward-inclusive: nearest resolving record in either direction, signed.
    gap_days_at_assignment = case_when(
      has_direct_zip9        ~ as.numeric(ADMIT_DATE - direct_zip_period_start),
      !is.na(gap_days_s2_any) ~ gap_days_s2_any,
      !is.na(gap_days_s3_any) ~ gap_days_s3_any,
      TRUE                    ~ NA_real_
    ),
    # Backward-only: backward matches only. Never negative by construction.
    gap_days_at_assignment_backward_only = case_when(
      has_direct_zip9        ~ as.numeric(ADMIT_DATE - direct_zip_period_start),
      !is.na(gap_days_s2_bwd) ~ gap_days_s2_bwd,
      !is.na(gap_days_s3_bwd) ~ gap_days_s3_bwd,
      TRUE                    ~ NA_real_
    )
  ) %>%
  select(-gap_days_s2_bwd, -gap_days_s2_any, -gap_days_s3_bwd, -gap_days_s3_any)

# 140-08-PATCH FIX-02: the backward-only covariate must never carry a forward-inferred
# value -- this is the invariant that makes "backward-only" a defensible label.
stopifnot(all(encounter_zip$gap_days_at_assignment_backward_only >= 0, na.rm = TRUE))
```

This also resolves the design question raised by 140-05's own test case (c), which asserts
a folded-S3 encounter carries `gap_days_at_assignment == -15`. Under the amended scheme
that encounter carries `-15` in the forward-inclusive column and `NA` in the backward-only
column — so the backward-only specification no longer contains forward-inferred gap values.

**Test additions.** Extend Task 1's fixture: case (c) asserts `-15` forward-inclusive and
`NA` backward-only; add a case (e) — forward-only S2 — asserting a negative value
forward-inclusive and `NA` backward-only.

## FIX-03 [M] — the S1 fold-in is conditional on D-2, with no recorded dependency

**Target:** 140-04 frontmatter (`depends_on`, `requirements`) and `<objective>`.

**Defect.** S1 is the rule that recovers a **ZIP9** (+4) for a ZIP5-only encounter by
matching against a prior ZIP9 sharing its ZIP5. Folding it into S3 discards that recovery
for 33,785 encounters and resolves them at ZIP5 precision instead.

That is coherent only if D-2 lands on ZIP5 as the analysis unit. If D-2 returns option-b
(defer pending the block-group re-run), or if P-03b later shows ZIP9 carries real utility at
block-group level, the fold is the wrong call and must be reverted.

D-2 is decided in 140-02. 140-04's `depends_on` is `[140-01, 140-03]` and its text never
references D-2.

**Change.**

- `depends_on: [140-01, 140-02, 140-03]`
- `requirements: [P-06a, P-06b, P-06c, P-06d, D-2, D-4]`
- Add to `must_haves.truths`: *"The S1 fold-in is explicitly recorded as conditional on
  D-2 = option-a (ZIP5 as analysis unit); if D-2 returned option-b, Task 1 is not executed
  and the 5-level ordered assignment is retained pending P-03b."*
- Add to `<objective>`: a paragraph stating the fold assumes D-2 = option-a, that it is
  reversible, and that `assign_scenarios()` is the single site to revert.

**Note on wave ordering.** 140-02 is Wave 1 and 140-04 is Wave 3, so D-2 is answered before
140-04 runs regardless. This fix records the logical dependency so the conditional is not
lost if waves are re-sequenced or a plan is re-run.

## FIX-04 [M] — the FIX-04d caveat inverts; it does not become unnecessary

**Target:** 140-04 Task 2 (KEY sheet field update).

**Defect.** 140-04 states the FIX-04d caveat "becomes unnecessary rather than restated."
It does not — it flips sign, and the new form is more confusing than the old.

Folded ordered S3 = all `has_direct_zip5_only` = old S1 (33,785) + old S3 (194,373) =
**228,158**. B_direction_split's unordered "S3-eligible" = 215,597, because
`s3_eligible = !s1_backward` excludes the 12,561 S1-backward encounters.

> 215,597 + 12,561 = 228,158 — the identity holds exactly and is worth asserting.

So the ordered S3 column will **exceed** the unordered S3-eligible column by 12,561.
Previously the ordered column undercounted. A reader comparing B_scenario_counts against
B_direction_split hits a fresh contradiction in the opposite direction, unexplained.

**Change.** Preferred: redefine `s3_eligible` to `has_direct_zip5_only` so ordered and
unordered agree, and relabel B_direction_split's row accordingly. This removes the
discrepancy rather than documenting it.

If `s3_eligible`'s current definition must be preserved for continuity with Phase 139
outputs, replace the KEY sheet field text with the inverted caveat stated plainly:

> Ordered vs unordered S3 (140-04 P-06b, amended by 140-08-PATCH FIX-04): S1 is no longer
> a distinct ordered bucket — every `has_direct_zip5_only` encounter is assigned "S3".
> The ordered S3 count therefore now EXCEEDS B_direction_split's unordered "S3-eligible"
> count by exactly the S1-backward count, because `s3_eligible` retains its
> complement-of-S1-backward definition. This is the inverse of the pre-fold relationship
> described by 139-05-PATCH FIX-04d. Use the ordered count for the assignment; use
> "S3-eligible" only for continuity with Phase 139 outputs.

**Also add** (Task 2, after both waterfalls are computed) a coverage-neutrality assertion.
The fold relabels buckets; it must not change total resolved coverage:

```r
# 140-08-PATCH FIX-04: the S1 fold-in is coverage-neutral by construction
# (old 74.4 + 1.7 + 11.0 + 9.8 = 96.9; new 74.4 + 11.0 + 11.5 = 96.9).
# Any drift here means assign_scenarios() changed scope, not just labels.
stopifnot(
  sum(encounter_zip$scenario_assigned != "unresolvable") ==
    sum(!encounter_zip$has_direct_zip9 &
        (encounter_zip$s2_either | encounter_zip$has_direct_zip5_only)) +
    sum(encounter_zip$has_direct_zip9)
)
```

## FIX-05 [M] — the "encounter-anchored" curve is not anchored on the encounter date

**Target:** 140-06 Task 1 (`build_encounter_anchored_validation_cases()`).

**Defect.** The planned `gap_days = as.numeric(direct_zip_period_start - period_start_dt)`
measures record-to-record elapsed time. `ADMIT_DATE` appears only as a grouping key.

The x-axis is therefore the same kind of quantity A-06 already plots. The sampling frame
genuinely improves — cases are now weighted by encounter frequency rather than
address-record frequency, which is the main bias P-05a exists to correct — but Task 2
instructs readers to read the two curves alongside each other, and on this definition they
are not comparable in the way that framing implies.

The production-relevant quantity is how stale the prediction was at the moment of lookup,
which is what `get_zip9_at_date()` actually experiences.

**Change.** In the `mutate()`:

```r
# 140-08-PATCH FIX-05: gap is measured from the ENCOUNTER date to the predicting
# record, not record-to-record -- this is the staleness get_zip9_at_date() sees in
# production, and it is what makes this curve readable against A-06's.
gap_days = as.numeric(ADMIT_DATE - period_start_dt),
```

Bin boundaries are unchanged. Note in the sheet subtitle that the two curves share bin
labels but differ in what the gap measures (A-06: record-to-record; P-05a: encounter-to-
predicting-record), so the comparison is of accuracy *levels* at comparable staleness, not
of identically-constructed quantities.

## FIX-06 [M] — unstated selection limitation on the encounter-anchored curve

**Target:** 140-06 Task 2 (sheet subtitle and KEY sheet field).

**Defect.** The curve requires `has_direct_zip9 == TRUE` — the 74.4% of encounters that
already carry a covering ZIP9. The 25.6% without one are exactly the encounters

> Limitation: this curve is computed only on encounters that already have a covering ZIP9
> (74.4% in the 08/06 run) — the encounters that need carry-forward are, by definition,
> the ones without ground truth to validate against. Both validation curves also compute
> ZIP5 accuracy from ZIP9-derived ZIP5, not `zip5_coalesced`, so ZIP5 accuracy is measured
> on the ZIP9-complete subpopulation only.

Add the same limitation as a KEY sheet field so the D-2 decision record carries it.

## FIX-07 [C] — universe cross-check false-positives on duplicate cohort IDs

**Target:** 140-07 Task 1.

**Defect.** `compute_c02()` computes `n_cohort_absent_from_addr` as
`sum(!(cohort_ids %in% addr_coal$ID))`, which counts duplicates. The planned cross-check
computes `length(COHORT_IDS) - length(intersect(...))`, and `intersect()` dedupes. With
`COHORT_IDS = c("A", "A")` and A present in `addr_coal`: left side gives 1, right side
gives 0, and the `stopifnot` fires on clean data.

Secondly, the check sits in SECTION 14, after all computation and immediately before
workbook assembly. On HiPerGator a false positive there costs a full run.

**Change.** Use `n_distinct()` on both sides and relocate the assertion to SECTION 12,
directly after `c02_result <- compute_c02(COHORT_IDS, addr_coal)`:

```r
# 140-08-PATCH FIX-07: n_distinct on both sides (compute_c02() counts duplicate cohort
# IDs; intersect() dedupes) and asserted early, so a mismatch fails in seconds rather
# than after the full run.
n_cohort_in_addr     <- n_distinct(intersect(COHORT_IDS, addr_coal$ID))
n_cohort_not_in_addr <- n_distinct(COHORT_IDS) - n_cohort_in_addr
stopifnot(n_cohort_not_in_addr == c02_result$n_cohort_absent_from_addr)
```

SECTION 14 then reads these as already-computed values. If `COHORT_IDS` can legitimately
contain duplicates, dedupe it at source in 139-03 Task 1 instead and note that here.

## FIX-08 [C] — tie-breaking on nearest-match reductions

**Target:** 140-05 Task 1 (`s1_nearest_any`, and FIX-01's `s2_nearest_any`).

an encounter with matches at exactly ±30 days resolves to `+30`.

## FIX-13 [G] — unparseable date strings are counted, then discarded

**Target:** 140-03 Task 2.

**Defect.** `unparseable_raw_sample` is classified into four categories and dropped. P-02b
requires deciding whether `parse_pcornet_date()` can be extended, which needs the actual
raw values — category counts do not support that decision. As planned, P-02b requires a
second HiPerGator round-trip, which is the cost this plan exists to avoid.

**Change.** Add a second QC table carrying the most frequent distinct raw values per
category:

```r
# 140-08-PATCH FIX-13: counts alone cannot answer P-02b -- carry the actual strings so
# the parser-extension decision can be made from one run, not two.
unparseable_date_examples <- tibble(raw_value = unparseable_raw_sample) %>%
  mutate(category = classify_unparseable_dates_vec(raw_value)) %>%
  count(category, raw_value, name = "n") %>%

  slice_max(n, n = 20, with_ties = FALSE) %>%
```
