the AMEND-01 ZIP5-coalesce are absent from `R/`, and Plans 01–04 are built on that finding.

grep -n "approximate_zip9\|zip9_source\|coalesce(normalize_zip5" R/utils/utils_address.R

Three outcomes:

- **Work exists and is committed** → CONTEXT's finding is wrong. Plan 01 must not add a second

## FIX-01 (BLOCKING) — Rewrite Plan 02's A-06 hold-out

### Problem

Plan 01 Task 3 collapses `zip9_seq` to one row per consecutive-distinct-ZIP9 spell:

```r
mutate(is_new_spell = row_number() == 1 | zip9_norm != lag(zip9_norm)) %>%
filter(is_new_spell)
```

Within a patient, consecutive `zip9_seq` rows therefore differ in `zip9_norm` **by definition**.
Plan 02 Task 1 then computes:

```r
predicted_zip9 = lag(zip9_norm)
exact_match    = predicted_zip9 == zip9_norm
```

`exact_match` is `FALSE` for every test case. `pct_exact_zip9_match` reads **0.0** in all five gap
bins and in the Overall row. The column is a tautology of the dedup step, not a measurement.

`zip5_match` is `TRUE` exactly when the transition was +4-only, so it reproduces A-01's
`n_plus4_only_transitions` as a percentage. The A_validation_curve sheet would carry one real
statistic already reported on another sheet, plus a column of zeros.

### The sampling problem underneath it

Every test case is a spell boundary — a case where the address changed — and `gap_days` is the
duration of the preceding spell. A-06 exists to answer "if a ZIP9 is carried forward N days, how
often is it still correct?" That probability is dominated by the cases where nothing changed, and
the current frame excludes all of them. It retains every failure and discards every success.

### Resolution — hold out a RECORD, not a spell

Operate on `addr_coal` (pre-dedup), not `zip9_seq`. For a lookup date where the covering record has
a non-NA ZIP9 (truth known), remove **that record only**, then apply the production rule — most
recent prior record with a non-NA ZIP9 — and compare. Patients with repeated records at an
unchanged address then yield correct predictions, which is where the accuracy lives, and
`gap_days` varies within a spell according to where the lookup date falls.

**Pick a framing (Claude's Discretion, both valid):**

| Framing | Lookup dates | Wave |
|---|---|---|
| **F1 — address-record-anchored** *(recommended)* | each `addr_coal` record's `period_start_dt` | Plan 02 stays wave 2, depends only on 139-01 |
| **F2 — encounter-anchored** (matches CONTEXT A-06 literally) | `ADMIT_DATE` from Plan 03's `encounters` | Plan 02 moves to **wave 4**, `depends_on: [139-01, 139-03]` |

F1 keeps the existing wave order and needs no ENCOUNTER pull. F2 matches the CONTEXT text and
measures the production path exactly. If F2 is chosen, renumber so xlsx assembly stays last.

### Replacement for Plan 02 Task 1 (F1 shown)

```r
    # A-06: hold out one address RECORD (not a spell) and predict it from the most recent
    # prior record with a non-NA ZIP9 -- the same rule get_zip9_at_date() applies.
    # Operates on addr_coal, NOT zip9_seq: spell-collapsing removes exactly the
    # unchanged-address cases that carry-forward is supposed to get right.
    holdout_base <- addr_coal %>%
      filter(!is.na(zip9_norm), !is.na(period_start_dt)) %>%
      arrange(ID, period_start_dt, desc(period_end_dt))

    validation_cases <- holdout_base %>%
      group_by(ID) %>%
      mutate(
        predicted_zip9  = lag(zip9_norm),         # prior RECORD -- may repeat the same address
        predicted_start = lag(period_start_dt),
        gap_days        = as.numeric(period_start_dt - predicted_start)
      ) %>%
      ungroup() %>%
      filter(!is.na(predicted_zip9))
```

Everything downstream (`exact_match`, `zip5_match`, `gap_bin`, the Overall row, the block-group
probe) is unchanged and correct once the input is right.

Two reporting additions the corrected frame makes possible and worth having:

```r
    # Share of test cases where the address did not change -- the base rate the curve is
    # measuring against. If this is near zero, addr_coal is more deduplicated than expected
    # and the curve is still not measuring what A-06 intends.
    pct_unchanged <- round(100 * mean(validation_cases$exact_match), 1)

    # Same-day records: gap_days == 0 means two records share a period_start_dt. These are
    # version corrections, not elapsed-time tests. Report separately, do not fold into "0-30".
    n_same_day <- sum(validation_cases$gap_days == 0, na.rm = TRUE)
```

Add a `"0 (same-day)"` bin ahead of `"0-30"`, and redefine `"0-30"` as `1 <= gap_days <= 30`.
Same-day pairs are record-keeping artifacts and will otherwise inflate the shortest bin's accuracy.

### Also correct the reasoning, not only the code

Plan 02's interfaces block justifies the spell universe from Pitfall 1 and reinterprets CONTEXT's
"target encounter" as "the target lookup date being tested," recording the reinterpretation as a
Claude's-Discretion note for the KEY sheet.

Pitfall 1 says *change counts* differ between the address-history and encounter universes, so every
table must state which it uses. It is not a rule that every Part A sheet must be computed on
address history, and it does not speak to A-06 at all. A-06's own text is explicit: "Take
encounters that **do** have an observed ZIP9."

Remove the reinterpretation from Plan 02's interfaces block and from Plan 04's KEY-sheet
Claude's-Discretion list. Under F1, the KEY sheet should say instead: *A-06 is computed on
address-history records, using each record's period start as the lookup date; this measures the
same carry-forward rule the encounter path applies.*

## FIX-02 (BLOCKING) — Open-ended address records are dropped in Plan 03

### Problem

Plan 03 Task 1:

```r
filter(period_start_dt <= ADMIT_DATE, ADMIT_DATE < period_end_dt)
```

A patient's current address normally carries `period_end_dt = NA`. `ADMIT_DATE < NA` evaluates to
`NA`, and `filter()` drops `NA`. **Every encounter whose covering record is the current address is
therefore classified `has_neither`.**

This is not an edge case — it is most recent encounters. `has_direct_zip9` is understated, `S2` is
overstated, and Part C's waterfall is wrong at every step. The plan cites `get_zip9_at_date()`
lines 111–130 as the model, but the quoted snippet omits that function's end-date handling.

### Resolution

Coalesce before comparing, in `addr_coal` (Plan 01 Task 2) so every consumer inherits it:

```r
    PERIOD_END_SENTINEL <- as.Date("9999-12-31")

    addr_coal <- addr_coal %>%
      mutate(
        period_end_open = is.na(period_end_dt),
        period_end_eff  = coalesce(period_end_dt, PERIOD_END_SENTINEL)
      )

    message(glue("[R/115] {sum(addr_coal$period_end_open)} address record(s) are open-ended ",
                 "(NA period_end_dt); treated as current through {PERIOD_END_SENTINEL}"))
```

Then in Plan 03 Task 1: `filter(period_start_dt <= ADMIT_DATE, ADMIT_DATE < period_end_eff)`.

Report `sum(period_end_open)` on the QC sheet. If it is zero, verify that against the raw file
before trusting it — an address history with no open intervals is unusual and more likely indicates
that end dates were imputed upstream.

**Also apply the sentinel in FIX-04's exposure span.**

## FIX-03 (BLOCKING) — C-02 compares two different populations

### Problem

Plan 04 Task 1:

```r
n_patients_no_zip5_ever <- addr_coal %>%
  group_by(ID) %>%
  summarise(all_na_zip5 = all(is.na(zip5_coalesced)), .groups = "drop") %>%
  summarise(n = sum(all_na_zip5)) %>% pull(n)
```

Three defects:

1. **Patients with zero rows in `addr_coal` are invisible.** Plan 01 drops unparseable dates and
   out-of-study-period rows before this point. A patient whose every record falls outside
   2012-01-01–2025-03-31 has no group, so `group_by()` never sees them and they contribute 0 —
   though they are exactly the "no usable ZIP5" population C-02 is counting.
2. **Wrong denominator.** The notes' 26 counts patients in the Hodgkin lymphoma study cohort.
   `addr_coal` is every patient in `LDS_ADDRESS_HISTORY`, which no plan filters to the cohort.
   Plan 03's `ENCOUNTER` pull is likewise unfiltered.
3. **The ±5 tolerance hides both.** A tolerance is reasonable for cohort-definition drift. It
   cannot absorb a denominator mismatch of unknown magnitude, and a passing check under the wrong
   denominator is worse than a failing one — it certifies a deliverable that was never validated.

### Resolution

**03a — Define the cohort explicitly.** Add a cohort patient vector near the top of R/115, sourced
the same way the other investigation scripts define their study population (read R/106 and R/111 to
find the established pattern; do not invent a new one). Restrict both `addr_coal` and the
`ENCOUNTER` pull to it, and log the cohort N.

**03b — Count over the cohort, not over addr_coal.**

```r
    cohort_ids <- tibble(ID = COHORT_IDS)

    zip5_ever <- addr_coal %>%
      group_by(ID) %>%
      summarise(has_any_zip5 = any(!is.na(zip5_coalesced)), .groups = "drop")

    c02_tbl <- cohort_ids %>%
      left_join(zip5_ever, by = "ID") %>%
      mutate(has_any_zip5 = coalesce(has_any_zip5, FALSE))   # absent from addr_coal => no ZIP5

    n_patients_no_zip5_ever <- sum(!c02_tbl$has_any_zip5)
    n_cohort_absent_from_addr <- sum(!(cohort_ids$ID %in% addr_coal$ID))
```

**03c — Report the pre-filter count alongside.** Compute the same statistic against the address
data *before* the study-period and unparseable-date filters, and report both. A large gap means the
filters are removing patients that C-02's control total includes, and the tolerance should not be
what absorbs that.

**03d — Keep the tolerance, narrow its claim.** `C02_TOLERANCE <- 5L` is fine for cohort-definition
drift once the denominator is right. Document it in the KEY sheet as covering cohort-definition
differences only — not as slack for methodological uncertainty.

## FIX-04 — Shorter corrections

**04a — `ADDRESS_ZIP5` branch is the phase's single point of failure (Plan 01 Task 2).**
The conditional silently degrades to derived-from-ZIP9-only when the column is absent — the exact
state this phase exists to escape. Everything downstream then measures nothing and C-02 fails with
no indication why. Log the branch loudly and stop rather than fall back:

```r
    has_raw_zip5 <- "ADDRESS_ZIP5" %in% names(addr_raw)
    message(glue("[R/115] raw ADDRESS_ZIP5 column {if (has_raw_zip5) 'FOUND' else 'NOT FOUND'}"))
    if (!has_raw_zip5) {
      message("[R/115] Without a raw ZIP5 column, ZIP5 can only be derived from ZIP9 and every ",
              "ZIP5-only record remains invisible. This phase's premise does not hold. ",
              "Print names(addr_raw), identify the correct source column, and re-run.")
      print(names(addr_raw))
      quit(status = 0)
    }
```

R/106 lines 202–230 reportedly already coalesce, which suggests the column exists — confirm rather
than infer.

**04b — Exposure span ignores `period_end` (Plan 01 Section 5).**
`max(period_start_dt) - min(period_start_dt)` gives a patient with two records 30 days apart — the
second running ten years — a 30-day span and a wildly inflated transitions-per-year rate. Use
`max(period_end_eff) - min(period_start_dt)`, with the FIX-02 sentinel replaced by the data
extraction date rather than 9999-12-31 for this calculation only (a sentinel end date makes every
open-ended patient's span ~7970 years and drives every rate to zero). Define
`DATA_THROUGH <- ZIP_STUDY_PERIOD_MAX` and cap with `pmin(period_end_eff, DATA_THROUGH)`.

**04c — `semi_join` pre-filter should be the default (Plan 03 Task 1).**
The plan defers it pending profiling. It is free, strictly reducing, and the `many-to-many` join it
guards is the largest operation in the script. Make it default; drop the "unless profiling shows it
is needed" language. FIX-03a's cohort restriction subsumes most of this but does not replace it.

**04d — Ordered S3 is not the notes' S3 (Plan 03 Task 2).**
S3 eligibility is defined as the complement of S1-*backward*, but the ordered assignment tests
S1-*either* first. An encounter eligible only via S1-forward is assigned `S1` while still being
S3-eligible. Both counts are reported so nothing is lost, but the KEY sheet must state that the
ordered `S3` column and the unordered `S3-eligible` column are different quantities — otherwise the
ordered column will be read as the notes' S3 and under-report it.

**04e — `has_neither` conflates two states (Plan 03 Task 1).**
"No covering record exists" and "a covering record exists with both fields NA" are different data
conditions, and the notes' S2 presumes a record exists. Split into `has_no_record` and
`has_record_but_empty`, report both, and keep their union as `has_neither` for the scenario logic.

## FIX-05 — Verification is structural only

Every `<automated>` block in all four plans is a grep for a string in the file. A file containing
`exact_match` passes regardless of what it computes — which is why FIX-01 survived planning. Four
tasks carry `tdd="true"` with no behavioral assertion anywhere.

**Add `tests/testthat/test-115-validation-curve.R`** with a synthetic fixture, and treat it as the
acceptance gate for Plan 02:

- **Stable patient:** five address records, same ZIP9, spread over three years, one per ~9 months.
  Assert the A-06 exact-match rate is **100%**, and specifically that it is not 0. *Under the
  current Plan 02 design this test returns 0% — it is the test that catches FIX-01.*
- **Mover:** four records at ZIP9-A then three at ZIP9-B. Assert exact-match is high in the short
  gap bins and drops at the transition; assert the rate is strictly between 0 and 100.
- **+4-only mover:** records at `32611-1234` then `32611-5678`. Assert `exact_match` is FALSE and
  `zip5_match` is TRUE for the transition case.
- **Single-record patient:** contributes zero test cases and increments `n_excluded_no_prior`.
- **Open-ended interval (FIX-02):** an encounter after a record with `period_end_dt = NA` is
  classified `has_direct_zip9`, not `has_neither`.
- **C-02 (FIX-03):** a cohort patient with no rows at all in `addr_coal` counts toward
  `n_patients_no_zip5_ever`.

The first assertion is the one that matters. A curve reading 0.0 across every bin looks like a
finding — "carry-forward never works" — rather than a bug, and would plausibly be reported to the
team as such.
