  <behavior>
    For each (ID, ADMIT_DATE) encounter, find the addr_coal record whose interval covers
    ADMIT_DATE (period_start_dt less-or-equal ADMIT_DATE, ADMIT_DATE less-than period_end_dt),
    preferring a non-NA zip9_norm record and breaking remaining ties by most-recent
    period_start_dt (same tie-break priority as get_zip9_at_date()'s own interval_hits logic,
    utils_address.R lines 121-130 -- replicated here, not called, because the coalesced ZIP5 is
    needed alongside it).
    - has_direct_zip9 = an interval-covering record exists AND its zip9_norm is not NA
    - has_direct_zip5_only = an interval-covering record exists AND its zip9_norm is NA AND its
      zip5_coalesced is not NA
    - has_neither = no interval-covering record exists, OR one exists with both zip9_norm and
      zip5_coalesced NA
    These three are mutually exclusive and exhaustive over all encounters.
  </behavior>
  <action>
Append to R/115_zip_stability_counts.R (Section 10, with a Part B header comment block marking
the universe as "encounters" per Pitfall 1 -- distinct from Part A's address-history universe).

Pull ENCOUNTER using the pattern given in this plan's interfaces block above.

Compute the top-1 interval match per (ID, ADMIT_DATE) via a per-patient join followed by an
interval filter and a group-wise slice(1), the same shape as get_zip9_at_date()'s own
interval_hits computation (utils_address.R lines 111-130) but reading zip5_coalesced instead of
the function's own derived-only ZIP5:

    encounter_zip <- encounters %>%
      left_join(
        addr_coal %>% select(ID, zip9_norm, zip5_coalesced, period_start_dt, period_end_dt),
        by = "ID", relationship = "many-to-many"
      ) %>%
      filter(period_start_dt <= ADMIT_DATE, ADMIT_DATE < period_end_dt) %>%
      group_by(ID, ENCOUNTERID, ADMIT_DATE) %>%
      arrange(is.na(zip9_norm), desc(period_start_dt), .by_group = TRUE) %>%
      slice(1) %>%
      ungroup() %>%
      select(ID, ENCOUNTERID, ADMIT_DATE, direct_zip9 = zip9_norm, direct_zip5 = zip5_coalesced)

    encounter_zip <- encounters %>%
      left_join(encounter_zip, by = c("ID", "ENCOUNTERID", "ADMIT_DATE")) %>%
      mutate(
        has_direct_zip9      = !is.na(direct_zip9),
        has_direct_zip5_only = is.na(direct_zip9) & !is.na(direct_zip5),
        has_neither          = is.na(direct_zip9) & is.na(direct_zip5)
      )

Pitfall-5-style note: the left_join above builds a per-patient candidate set before the interval
filter, which is fine at this project's address-history row counts (unlike the multi-million-row
DIAGNOSIS table R/111 pushes into DuckDB before collecting). If this proves too slow on the real
HiPerGator ENCOUNTER volume, restrict addr_coal to semi_join(encounters, by = "ID") BEFORE the
join to cut the candidate set to only patients actually queried (mirrors get_zip9_at_date()'s own
Pitfall-5 comment, utils_address.R line 109) -- note this as an optimization fallback in a code
comment, do not add the semi_join pre-filter by default unless profiling shows it is needed.

message() a headline count: n encounters total, n has_direct_zip9, n has_direct_zip5_only, n
has_neither -- both raw counts and percent of total.

  <name>Task 2: S1-S4 ordered and unordered scenario assignment with direction split</name>
  <files>R/115_zip_stability_counts.R</files>
  <behavior>
    Per-encounter scenario eligibility (independent, unordered -- computed BEFORE the S1-then-S2-
    then-S3 ordering is applied):
    - S1 eligible backward: has_direct_zip5_only AND a zip9_seq spell exists for the same patient
      with period_start_dt less-or-equal ADMIT_DATE whose ZIP5 (first 5 chars of zip9_norm)
      equals direct_zip5.
    - S1 eligible forward: same condition but period_start_dt greater than ADMIT_DATE.
    - S1 eligible either: backward OR forward.
    - S2 eligible backward: has_neither AND a zip5_seq spell exists for the same patient with
      period_start_dt less-or-equal ADMIT_DATE. zip5_seq (not zip9_seq) is used because S2 covers
      BOTH the "take a ZIP9 from another encounter" path and the "ZIP5 centroid" path -- any
      backward zip5_seq spell satisfies at least the centroid path; if that spell also has a
      non-NA zip9_norm it satisfies the take-ZIP9 path too. Add a resolution_path column
      ("take_zip9" if the nearest backward zip5_seq spell also has zip9_norm non-NA, else
      "centroid_only") for transparency in the eventual B_scenario_counts sheet -- computed for
      reporting, not used to gate S2 eligibility itself.
    - S2 eligible forward: same condition but period_start_dt greater than ADMIT_DATE, using
      zip5_seq.
    - S2 eligible either: backward OR forward.
    - S3 eligible (backward only -- S3's own definition is inherently backward, "does not match
      the PRIOR ZIP9's ZIP5"): has_direct_zip5_only AND NOT S1-eligible-backward. (S1-backward and
      S3 are complements within the has_direct_zip5_only set by construction -- a ZIP5-only
      encounter either matches some earlier ZIP9's ZIP5, S1, or it does not, S3.)
    - S4 (complete-case comparator, reported separately, not part of the ordered assignment): the
      complement of has_direct_zip9, i.e. every encounter that is NOT already-has-ZIP9. Report as
      "excluded under S4" = count of !has_direct_zip9, both encounter and patient level.

    Ordered assignment (S1 then S2 then S3), one column scenario_assigned per encounter:
    - "already_has_zip9" if has_direct_zip9
    - else "S1" if S1-eligible-either
    - else "S2" if S2-eligible-either
    - else "S3" if S3-eligible
    - else "unresolvable" (has_neither with no backward or forward ZIP5/ZIP9 anywhere for the
      patient -- this residual feeds Part C's completeness waterfall in Plan 04)
  </behavior>
