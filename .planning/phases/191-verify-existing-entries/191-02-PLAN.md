<definitions>

## Verdict rules

| Verdict | Use only when |
|---------|---------------|
| `MATCH` | The code path implements what the manual states (cited `CODE`/`CONFIG`), and any query evidence for the item comes from a COMPLETE check and is consistent with it. For a statement that only describes the data (an "Observed issue"), MATCH means the query confirms the described issue exists in this extract. |
| `MISMATCH` | The code path does something materially different from the manual statement, or the query shows the manual's described behavior does not hold. |
| `PARTIAL` | Part of the statement matches and part does not (e.g., one of two steps differs; rule applied to HL only where the manual says all types). |
| `CANNOT-VERIFY` | The code path cannot be located, or the needed check is SKIPPED/FAILED/PARTIAL and code reading alone cannot settle it. State what is missing. |
| `BLOCKED` | Depends on an input not received (c0). |

Observed-only evidence (a query result with no code-path citation) can support MISMATCH or
CANNOT-VERIFY, never MATCH for a behavior claim.

## Evidence types
`CODE`, `CONFIG`, `QUERY` (cite `am_verification_<date>.xlsx:<sheet>`), `PLANNING-DOC`, `TEAM-DECISION`.

## Decision rows
- A decision row is needed for every MISMATCH and PARTIAL.
- Status `CONFIRMED` only when an existing decision in AM-MAP-03 already settles the difference:
  Original ID = that decision's ID; Decided By and Date copied from it; Notes "Manual update only;
  no new team decision needed."
- Otherwise Status `OPEN`; Decided By and Date `—`.
- Decision text states the difference neutrally (manual says X; code does Y) and the question to
  the team. It does not assert values not yet confirmed in evidence.

</definitions>
