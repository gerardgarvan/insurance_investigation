<objective>
Write a standalone, read-only R script that runs the six query-backed checks and writes
`am_verification_<YYYYMMDD>.xlsx`. The script produces results and a machine-readable status per
check; it never writes verdicts. A human checkpoint runs it on HiPerGator.

Verification design (applies to every check):
- **Manual side:** the manual's rule implemented directly in SQL on the CDM tables (D-01a).
- **Pipeline side:** the pipeline's own result. Preferred: call the pipeline function live in the
  same session, against the same DuckDB connection, so both sides share one data snapshot.
  Fallback (logic lives only in a script's output): read the saved artifact and record in QC its
  exact filename, modification time, the exact filename of the upstream input it was built from
  (e.g. which `encounter_distance_*.rds` an R/116 output used — unpinned inputs drift; see the
  2026-11-04 R/165 regression, Oct 6 vs Oct 15 distance file), and the DuckDB file's modification
  time. An artifact-based comparison cannot be COMPLETE if its snapshot cannot be tied to the
  current DuckDB build; it is PARTIAL with that reason. Calling the pipeline function
  **as the comparison side** is correct; using it **as the manual side** is circular and not allowed.
- **Completion criteria (applies to every check):** each check declares a `required` vector of
  component names (listed per check below). Each component records `ok` (TRUE/FALSE), `n_in`
  (input rows/patients considered) and `n_compared`. `run_check()` derives the status:
  COMPLETE = every required component `ok` and, for comparison components, `n_compared == n_in`
  on both sides (records on one side only are reported, not dropped, and count as compared);
  PARTIAL = at least one required component ran but not all (Reason lists the missing ones);
  SKIPPED = a required input is absent before any component runs; FAILED = an error was caught.
  A query that returns rows is not by itself a COMPLETE check.
- **Observed vs implemented:** a query result describes this extract. Whether the code enforces a
  rule is a code-reading question answered in Plan 02. Each V-sheet states which of the two it
  supports.
</objective>

- Column-name constants from Task 0, each with its `file:line` comment.
- Use the project's existing `suppress_small()`; do not redefine it. Add a local
  `sup_table()` that applies `suppress_small()` to every count cell and complementary suppression to
  totals (same rule as R/169 `sup_with_totals()`: if exactly one interior cell of a row/column is
  suppressed, suppress that total too), and blanks any percentage derived from a suppressed count.
- Push filtering, grouping and patient-day collapsing into DuckDB SQL; collect only aggregated or

**Check runner.** Each check is a function returning
`list(required, components, reason, map_ids, provenance, tables, internal)`, where `required` is
the character vector of component names and `components` is a named list of
`list(ok, n_in, n_compared, note)`. The check function does **not** set its own status.
`run_check()` wraps it in `tryCatch` and derives status per the Completion criteria: an error →
`FAILED` with the message; a required input absent before any component ran → `SKIPPED`; some but
not all required components `ok` (or a comparison with `n_compared < n_in`) → `PARTIAL` with the
missing component names in Reason; all `ok` with full coverage → `COMPLETE`. QC records the
component list with ok/n_in/n_compared for every check. One failing check never stops the others.

**V1_SOURCE** (L1; map IDs from the live map)
- SOURCE (normalized `UPPER(TRIM())`, blank → NULL) by table for DEMOGRAPHIC, ENCOUNTER and every
  other CDM table that has a SOURCE column (detect via `information_schema.columns`, not trial and
  error): rows and patients, whole extract and HL cohort.
- HL cohort = IDs from `get_hl_any_dx_ids()` (cohort membership is not under test in V1).
- LNK rows/patients per table; patients with >1 distinct SOURCE per table, as counts by band.
- Note on sheet: "Observed in this extract; R/169 reads SOURCE from ENCOUNTER only."
- Tables without a usable patient key column report row counts only; the patient-count cell is
  "n/a — no patient key" (never invented).
- Required components: `source_by_table`, `lnk_by_table`, `multi_source_bands`.

**V2_INSURANCE** (L2 and the Insurance confirm row)
- Manual side: SQL implementing the six-level same-day hierarchy, collapsed to one value per
  patient-day in DuckDB.
- Pipeline side: resolved same-day payer per patient-day (Task 0 source; live call preferred;
  SKIPPED if the R/36 output is absent and no live call is possible).
- Comparison universe: HL-cohort patient-days with ≥1 ENCOUNTER row (date = ADMIT_DATE cast to
  DATE); one row per (ID, date) on each side after collapse; duplicates on either side after
  collapse are a FAILED component, not silently dropped.
- Outputs: (a) agreement after mapping pipeline categories through the Task 0 crosswalk, with the
  denominator stated (patient-days present on both sides and mapped); (b) full cross-tab of manual
  level × original pipeline category; (c) UNMAPPED categories reported separately; (d) patient-days
  present on one side only, counted on the sheet — these and UNMAPPED rows never disappear from
  the coverage totals.
- Discordant patient-days with IDs → `internal/am_v2_discordant_<run_date>.rds`.
- Required components: `manual_side`, `pipeline_side`, `crosswalk_agreement`, `crosstab`,
  `one_sided`.

**V3_DXDATE** (L3, c1)
- Manual side: two-step rule from Task 0 (HL registry date, else first C81/201 code date).
- Pipeline side: `get_hl_any_dx_ids()` anchor, called live.
- Outputs: anchor-source breakdown on each side (registry / code fallback / none; pipeline side
  labelled "inferred" if Task 0 found the function does not expose its source); agreement count;
  day-difference bands (0, 1–7, 8–30, 31–365, >365, and negative); patients on one side only.
- Required components: `manual_anchor`, `pipeline_anchor`, `source_breakdown`, `day_diff_bands`,
  `one_sided`.

**V4_DXSCOPE** (L4)
- Manual side: re-derive qualifying (ID, cancer_type) pairs directly from DIAGNOSIS under the
  manual's rule — ≥2 encounters with a code for that cancer type, on dates ≥7 days apart (date
  field from Task 0), ICD-9 and ICD-10 handled via DX_TYPE, code→category mapping from Task 0.
- Pipeline side: confirmed (ID, cancer_type) pairs as assigned by the pipeline (Task 0 source).
- Compare at (ID, cancer_type) grain **before** aggregating, both directions: manual-only
  (pipeline missed), pipeline-only (pipeline included a pair the rule rejects), both. Report the
  three counts by cancer category; HL reported for reference. Pair-level discordance with IDs →
  `internal/am_v4_discordant_<run_date>.rds`.
- Sheet note: "Observed agreement does not show that the code applies the rule to non-HL types;
  see Task 0 code-path finding," with the Task 0 finding quoted.
- Required components: `manual_pairs`, `pipeline_pairs`, `pair_comparison`.

**V5_ZIPCOVER** (L5 data side; descriptive)
- Patient level from LDS_ADDRESS_HISTORY: patients with any usable ZIP9, ZIP5 only, none (usable =
  non-null, non-sentinel per `utils_address.R`).
- Encounter level from the R/116 output (provenance per the fallback rule: exact filename and
  upstream distance file): encounters by `match_type` and `zip9_source` (exact values from
  Task 0), and with non-missing `adi_natrank` / `sdi_score`.
- Index source split (CONTEXT D-05): encounters and patients receiving ADI vs SDI vs neither, each
  split into directly assigned vs imputed (imputation values from Task 0, e.g. ZIP5-modal or
  centroid ZIP9).
- ZIP5→ZIP9 carry-over: encounters whose ZIP9 was carried over or imputed from a ZIP5 (Task 0
  values), as counts.
- Sheet note: "Encounter-level coverage reflects the pipeline's temporal assignment; it describes
  coverage, it does not verify the assignment rule."
- Required components: `patient_zip_coverage`, `encounter_match_type`, `index_source_split`,
  `zip_carryover`.

**V6_DEATH** (L6)
- Using the Task 0 aggregation rules: gap = death date − last treatment date, banded
  (death on/after last treatment; before by 1–14, 15–30, 31–90, >90 days; missing).
- Three separately labelled results on one patient universe (HL cohort with a death record):
  (1) manual: death dated >14 days before last treatment → removed, computed independently in
  SQL; (2) production-rule replay: the same computation at each production `grace_days` value
  from Task 0 (e.g. 30 at R/52); (3) actual production outcome: `resolve_death_date()` called live
  at each production call site's `grace_days`, excluded = per Task 0 (e.g. `death_date_resolved`
  NA). Report removed counts for each and pairwise disagreements (1 vs 3, 2 vs 3), plus patients
  missing from any side. A 2-vs-3 disagreement means the replay does not reproduce production and
  is flagged in Reason.
- Pair-level disagreements with IDs → `internal/am_v6_discordant_<run_date>.rds`.
- DEATH_CAUSE: (a) cohort patients with any DEATH_CAUSE record (descriptive); (b) the Task 0
  code-path finding on whether any inclusion/exclusion predicate uses it. Report (a) and (b)
  separately; never infer (b) from (a).
- Required components: `gap_bands`, `manual_removed`, `replay_removed`, `production_removed`,
  `pairwise`, `death_cause`.

- Save to `file.path(CONFIG$output_dir, glue("am_verification_{run_date}.xlsx"))`.

**Do not:** use the pipeline function as the manual side; write IDs, per-patient dates or ZIPs to
